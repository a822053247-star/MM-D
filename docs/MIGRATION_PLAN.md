## 3. 技术路线与源码管理

### 3.1 模块职责

| 层 | 职责 | 主要文件/拟建模块 |
|---|---|---|
| 规则 | 战斗、构筑、掉落、波次、商店、存档数据结构 | `src/core/`，后续按实际依赖补充 |
| 流程 | 菜单、加载、战斗、升级、商店、结算与地区切换 | `src/main.ts`、`src/model.ts`，扩展时拆为流程模块 |
| 平台 | 抖音输入、资源、音频、存储、前后台与窗口能力 | `src/platform.ts`、`src/audio.ts` |
| 表现 | 场景、角色、敌人、特效、UI与触摸命中区域 | `src/view.ts`、`src/hud.ts`、`src/input.ts`，按功能拆分 |
| 发布 | 显式资源清单、分包、体积、版本与发布前检查 | `scripts/`、`config/`、`resources/` |

不把原`game.ts`及DOM界面整体复制进新入口。先定义游戏状态与界面动作，再使用Canvas/WebGL呈现；不以补齐HTML/CSS模拟作为迁移路线。

### 3.2 固定迁移基线

- M1开始时记录原仓库HEAD、未提交文件清单和本次采用文件的内容哈希。原仓库当前有未提交改动，不能只用提交号代表完整基线。
- 每批新增源码与资源都记录来源、改动和使用场景。`import-source.mjs`仅手动使用，不在普通构建中自动覆盖快照。
- 移植规则时优先保持原模块接口；平台差异放在适配层。确需修改规则模块，单独记录差异并验证。
- 后续同步原项目采用逐项差异审查，不整目录覆盖已经适配的代码。

### 3.3 引擎决策关口

Three.js 0.186.1及其定制构建补丁目前只是已在本地验证的技术路线。M1需要检查真实抖音环境的WebGL 2、原生Image/Canvas上传、实例绘制、图集UV、中文UI和音频行为。

若代表性设备均可运行，则保留现有技术栈。若出现明确兼容故障，先制作最小复现，区分API适配问题和设备能力缺失；能局部修复的先修复。若目标设备范围无法满足WebGL 2要求，再比较支持目标能力的渲染版本/后端与Cocos迁移成本，形成单独决策。不得通过关闭检查或让启动失败提示充当兼容完成。

## 5. 包体与资源分发计划

### 5.1 两种指标分别管理

1. **包体：** 主包、每个代码/资源分包、全部上传包体。分包只改变下载时机，不自动降低总包体。
2. **首局下载：** 冷启动至所选角色/地区首局可玩实际需要的主包、分包和远程资源。后续扩展不能只统计固定的`first-play/`。

现有`size-lib.mjs`仅计算主包加`first-play/`。开放角色选择或不同起始地区前，需改为按场景依赖清单计算，并对所有可作为新用户起点的组合验证10 MiB上限。远程资源也计入，不能通过移到CDN规避统计。

### 5.2 内部预算

| 内容 | 规划预算 | 处理方式 |
|---|---:|---|
| 主包 | ≤3 MiB；建议2.5 MiB时预警 | 平台入口、最少公共代码、必要UI；超预算前拆模块 |
| 冷启动首局所需内容 | ≤10 MiB；建议9 MiB时预警 | 默认角色、起始地图、可出现敌人、基础攻击、UI和音频 |
| 其余内容 | 按使用场景加载 | 后续地区、角色、Boss、进阶构筑、捕捉/囚坊 |
| 全部上传包 | 内部先按≤18 MiB规划 | 为平台封装和版本变化留余量，工具最终结果为准 |

截至制定日，抖音官方文档列出的默认整体包限制为20 MB，主包4 MB，开通虚拟支付后的整体包可到30 MB。本工程采用更严格的3 MiB主包目标，且不依赖开通虚拟支付来获得更大空间。MB与MiB计量口径不同，发布前必须核对工具字节数。[官方代码包说明](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/basic-function/subpackages/introduction)

### 5.3 资源流水线

- **M1：** 保留当前七项资源，补齐工具与真机实测；不提前引入CDN。
- **M2：** 建立显式资源注册表和依赖校验；卡框按实际尺寸输出，适合的面板采用九宫格，音频按需加载。
- **M3：** 输出运行图集/卡图，不发布源图；按内容绑定图集、锚点、UV与许可来源，压图后进行视觉复核。
- **M4前：** 预计超过上传预算时采用HTTPS对象存储/CDN。实现版本哈希、本地文件缓存、下载去重、失败重试、空间不足清理和旧版本回收；代码仍通过平台认可的主包/分包机制发布。
- **每批：** 资源文件体积与解码后CPU/GPU内存分别检查。WebP压小文件不等于等比例降低纹理内存；不为了减少文件数盲目合并超大图集。
